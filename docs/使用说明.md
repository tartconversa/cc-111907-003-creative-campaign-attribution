# 使用手册：AI 内容活动的增量贡献与预算续投

本应用在本地合成资料上运行，只用 Python 标准库（3.14）。它回答两类问题：

1. **下一轮广告还值不值得买？** 用事先登记、冻结的对照安排估计净贡献差异，
   给出不确定性、覆盖与成熟度，并区分“描述性路径”和“广告增量”。
2. **预算怎么落到下一轮？** 扣除已签约且不可取消的成本，比较候选活动的增量
   证据、剩余地区覆盖和预算上限，经负责人确认后才形成占用，并能回填下单、
   取消与执行。

所有结论都按数据截止点记录，可追溯到每次观察的原分配、受污染群体、决策理由
与预算去向。

---

## 1. 快速开始

```bash
# 1) 建一个隔离工作目录（来源目录只读）
python -m campaign_app init --work work --name demo --inputs inputs \
    --at 2026-10-31T00:00:00Z

# 2) 看来源是否干净
python -m campaign_app status --workspace work/demo
python -m campaign_app issues --workspace work/demo

# 3) 描述性路径（不是增量）
python -m campaign_app describe --workspace work/demo --cutoff 2026-11-18T00:00:00Z

# 4) 登记并冻结对照安排
python -m campaign_app design-create --workspace work/demo \
    --campaign fair \
    --planned-start 2026-11-01T00:00:00Z \
    --planned-end 2026-11-19T00:00:00Z \
    --observation-end 2026-12-01T00:00:00Z \
    --seed 20261101 \
    --allocation-basis "预注册：按相似层基线配对随机，观察前冻结" \
    --maturity-days 7 --max-looks 3 \
    --at 2026-10-31T00:00:00Z

# 5) 按计划观察
python -m campaign_app review --workspace work/demo --design-id D001 \
    --cutoff 2026-12-01T00:00:00Z --at 2026-12-02T00:00:00Z

# 6) 登记决策
python -m campaign_app decide --workspace work/demo --review-id R003 \
    --action pause --rationale "渠道覆盖存在缺口，先暂停并补齐投放" \
    --at 2026-12-02T00:00:00Z

# 7) 续投：先出方案，再确认，再回填执行
python -m campaign_app ledger --workspace work/demo --at 2026-12-02T00:00:00Z
python -m campaign_app propose --workspace work/demo --campaign fair \
    --regions G3,G11 --requested-fen 15000 \
    --start 2026-12-05T00:00:00Z --end 2026-12-20T00:00:00Z \
    --rationale "先小额探索并保留剩余预算" --at 2026-12-02T00:00:00Z
python -m campaign_app compare --workspace work/demo --proposal P001 \
    --proposal P002 --at 2026-12-02T00:00:00Z
python -m campaign_app confirm --workspace work/demo --proposal-id P001 \
    --rationale "负责人确认小额续投" --at 2026-12-02T01:00:00Z
python -m campaign_app execute --workspace work/demo --proposal-id P001 \
    --status signed --executed-fen 15000 --note "已下单" --at 2026-12-03T00:00:00Z

# 8) 审计：每次观察的截止点、原分配、决策理由与预算去向
python -m campaign_app audit --workspace work/demo
```

退出码：`0` 成功，`2` 业务拒绝（错误信息输出到 stderr，JSON 格式）。
所有命令输出 JSON，便于脚本化与复核。

## 2. 工作目录与隔离

```
work/<名字>/
├── state.json          # 方案、设计、观察、决策、预算台账（原子写入）
├── audit.jsonl         # 只追加的审计链（每条带前序哈希）
├── imports/<数据集>/   # 导入记录，按时间与哈希命名
└── exports/            # 预留导出目录
```

* 来源目录（默认 `inputs/`）**只读**，应用从不写回。
* 不同工作目录互不共享状态。`init` 拒绝覆盖已有目录；确需重建请用 `--replace`。
* 每次写入都持有目录锁，并以临时文件 + `os.replace` 原子替换。
* `audit` 会校验审计链；被改写或删除的事件会被报告为问题。

## 3. 数据契约要点与应用的落实

| 契约要求 | 应用行为 |
|---|---|
| 净贡献 = 收入 − 履约成本 − 退款 | 订单级计算；投放支出只计入活动总净价值，不在订单重复扣减 |
| `received` 是事实进入系统的时点 | 任何观察只用 `received <= cutoff` 的最新订单版本；历史版本保留 |
| 区间左闭右开、时间带时区 | 所有窗口用 `[start, end)`，缺少时区直接拒绝 |
| null 是缺失，不是 0 | 净贡献未知的订单使该单位值未知，并阻断自动判胜 |
| 重复投递不产生新事实 | 相同主键或相同业务载荷的重复回执只计一次，记录在问题清单 |
| 来源版本冲突须保留问题 | 同一身份同一版本内容不同 → 该身份不参与分析并报告 |
| 输入顺序无业务含义 | 所有汇总先按时间与主键排序 |
| 创意版本按上线时点解释 | 触达按当时已上线的最新版本归属；早于上线则报错 |

**已知输入缺口**：`touches` 没有 `received` 字段。应用按 `occurred < cutoff`
视为已知，并在每次观察的 `data_as_of` 中显式注明。若将来补充 `received`，
应在 `source.py` 中改为同样按接收时点截断。

导入新记录（不改来源文件）：

```bash
python -m campaign_app import --workspace work/demo --dataset orders \
    --file new_orders.json --note "补充迟到退款" --at 2026-12-05T00:00:00Z
```

导入会先按 `schema.json` 校验字段，再落入工作目录并记入审计。

## 4. 统计方法（可复现）

* **估计量**：处理组单位均值 − 对照组单位均值。默认按地区相似层分层，层内
  先算差异，再按常规客群规模加权；可选“层等权”和“不分层”。
  默认归一化为“每 1000 常规客群净贡献”，也可用总额。
* **不确定性**：层内自助法百分位区间；组随机化置换检验给双侧/单侧 p 值。
  分配组合不超过 20 万时**精确枚举**全部随机分配；否则用固定种子的蒙特卡洛，
  并记录抽取次数与最小可达 p 值。
* **多次查看**：按登记的最大查看次数做 O'Brien-Fleming 型 alpha 消耗，
  越早的查看判定阈值越严。`review` 自动按已完成的查看次数递增序号。
* **可复现**：设计的随机分组由 `seed + 活动 + 相似层` 决定；观察的置换与自助
  随机源由 `seed ^ look 常量` 决定，全部写入结果。同参数重复运行得到相同数值。
* **局限**：单位很少时检验力有限；每层只有 1 个单位时自助区间只是粗略近似；
  置换检验只覆盖“分配随机”这一不确定性，不能修复污染、覆盖缺口或未成熟订单。

预注册的对照口径（`stratified_baseline`）始终作为主要口径；另外两个口径同时
展示。只有主要口径显著而其他口径不显著或方向相反时，才判定“多口径不一致”。

### 退款成熟期与取消成熟期

订单有两个成熟期，都可显式登记：

* `--maturity-days`（取消成熟期）：订单要先过这个期限才计入净贡献，避免把
  仍可能取消的订单当成已实现。
* `--refund-maturity-days`（退款成熟期）：退款金额要再过这个期限才扣除。
  默认等于取消成熟期；不能短于它；观察截止点必须覆盖“计划终点 + 退款成熟期”。

每次观察的 `maturity` 守卫会同时给出 `mature_share` 与 `refund_mature_share`。

## 5. 对照安排与守卫

`design-create` 会冻结：

* 合格单位（默认全部地区，可用 `--regions` 限定）；
* 每个单位的分组、相似层与分配指纹；
* 主要指标（净贡献）、分析口径、归一化、alpha、置信水平、成熟期、最大查看次数；
* 计划投放区间与观察截止点；
* 预算上限。

拒绝登记的情况包括：分配未覆盖全部合格单位、某相似层缺少一组、单位过少、
观察截止点未覆盖“计划终点 + 成熟期”、预算超过活动上限、未登记分配依据。

**投放开始后才登记**会被拒绝，除非显式加 `--late-registration`。这样登记的
设计永久标记为非确认性（`confirmatory=false`），永远不会触发自动判胜。

每次观察给出守卫：

| 守卫 | 不通过的含义 |
|---|---|
| `maturity` | 订单未到成熟期，结论可能翻转 |
| `balance` | 相似层缺组、基线 SMD 过大或组规模差异过大 |
| `coverage` | 处理组有地区未实际投放，或对照组出现付费触达 |
| `missing_values` | 存在净贡献未知的订单（不能按 0 处理） |
| `contamination` | 同地区有其它活动的执行证据，且排除后结论不稳健 |
| `spec_robustness` | 预注册的多个口径结论不一致 |
| `observation_complete` | 尚未到达登记的观察截止点 |

`auto_win_eligible` 只有在**全部**守卫通过、主要口径显著为正、且设计为确认性
时才为真。应用**不会**替负责人做决定，`auto_win_eligible` 只是“可以按有效结束”
的必要条件。

**污染范围**：`contamination` 列出确有执行证据的其它活动（付费触达、合同、
已确认方案）及其重叠区间。原分配不会被删改；排除受污染单位只作为稳健性检查。
若同互斥组的活动日期重叠但本地区没有执行证据，会单独列在
`scheduled_elsewhere`，提示其对照可能被污染，但不改变本地区结果。

## 6. 观察计划与决策

* 查看次数超过登记上限 → 拒绝，必须先登记新版本。
* 截止点不能回退（同一设计必须随日历推进）。
* 每次观察只能登记一次决策。

决策规则：

* **继续**：存在任何阻断守卫时拒绝（应先暂停并说明修正方式）；已达最大查看
  次数也拒绝。
* **结束**：订单未成熟时拒绝。若结果显著为正但存在失衡/覆盖/缺失等数据问题，
  拒绝“有效结束”；可先暂停修正，或如实登记为“不判胜的结束”。
* **偏离**：与登记建议或计划时点不一致时，必须加 `--acknowledge-deviation`
  显式确认，记录中保留 `deviations` 与 `deviation_acknowledged`。

**改变观察计划或主要指标**用 `design-revise`：

```bash
python -m campaign_app design-revise --workspace work/demo --design-id D001 \
    --reason "观察到早期信号后调整观察计划" \
    --changes '{"observation_end":"2026-12-15T00:00:00Z","max_looks":2}' \
    --at 2026-12-03T00:00:00Z
```

新版本会标记 `version=2`、`supersedes=D001`，并且**只要此前看过结果**就
`confirmatory=false`、`prior_outcome_views=true`——已看过的结果不能被包装成
事先规定。看过结果后**不允许重新随机分组**（会破坏原分配）。

## 7. 预算续投

**剩余预算** = 总预算 − 不可取消的已签约合同 − 已执行合同 − 有效确认方案预留
− 已下单/已执行回填。可取消且未执行的合同不占用预算，但会在台账中单列。

**方案生命周期**：`proposed`（不占用）→ `confirmed`（占用，有有效期）→
`executed`/`cancelled`（以执行回填为准）。

* 方案必须写明理由；金额不能超过活动上限，也不能让活动累计占用超过上限。
* 同一地区同互斥组已被占用（合同或有效确认方案）时，不能再占用。
* **同一剩余预算或地区名额**：方案登记时快照剩余预算。若登记后已有其它确认
  或执行改变剩余预算，确认会失败并要求重新比较；同地区名额被占用也要求重新比较。
* **过期确认**：`expire` 列出已过期方案；过期方案不再占用预算或地区名额，但
  若与其它方案争用同一资源，必须重新比较后才能确认。

`compare` 按证据强度、地区冲突、金额排序，并列出证据状态：

| 证据状态 | 含义 |
|---|---|
| `supported` | 有确认性观察且自动判胜条件成立 |
| `not_supported` | 有观察但守卫未通过或不显著 |
| `no_confirmed_evidence` | 没有组随机化观察，不能把描述性路径当证据 |

`compare` 同时给出续投建议：

| 建议 | 含义 |
|---|---|
| `invest` | 守卫通过且证据支持，可按上限投放 |
| `pilot` | 证据有限，只支持小额试探 |
| `hold_budget` | 没有确认证据、地区名额冲突或预算不足，保留预算 |

执行回填：`--status signed|executed` 形成实际占用；`--status cancelled` 释放
占用（下单后取消按最新回填状态归零）。执行金额不能超过确认金额。

**迟到退款**（`refund-check`）区分两类：

* 已下单/已履约：合同与已发生成本保留（不能当成未花费），结论需修订
  （`revise_conclusion_not_contract`）。
* 已确认但未执行：进入重新审批（`reopen_review`），不能静默继续。

---

## 8. 不同活动并行

* 所有设计与观察都按活动隔离；`review` 只使用该设计冻结的活动、分配与口径。
* 不同活动可并行运行，各自的查看次数、暂停和续投互不串用。
* 同地区互斥只在“日期重叠且 `exclusive_family` 相同”时生效。

## 9. 测试

```bash
python -m unittest discover -s tests -v
```

测试分两类：

* `test_source_contract.py`：来源清单哈希、字段与时间格式。
* `test_business_rules.py`：用独立构造的合成夹具覆盖去重、版本、截止点、null、
  冻结分配、守卫阻断、序贯 alpha、偏离确认、预算占用、过期重比、执行回填、
  迟到退款重开、审计防篡改与工作目录隔离。

所有测试都在临时目录内运行，不读写仓库的 `inputs/`。
